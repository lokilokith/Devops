## 1. Project Identity & Architecture

### Current Direction
OpsForge is a **Privileged Access Management (PAM) platform**, NOT the earlier threat-intelligence version.

### Core Domain
- Credential vaulting with transparent envelope encryption
- Secret encryption via KMS abstraction
- Credential rotation automation  
- Role-Based Access Control (RBAC)
- Audit logging
- Lifecycle management with optimistic concurrency control
- Just-In-Time (JIT) privileged access
- Secure persistence with Compare-And-Swap (CAS) semantics

### Technology Stack
- **Backend:** Python 3.13, Flask, Flask-SQLAlchemy, Flask-RESTX
- **Database:** PostgreSQL (production), SQLite (testing)
- **ORM:** SQLAlchemy + Alembic
- **Security:** cryptography library, PyJWT, RBAC via permissions model
- **Testing:** pytest, pytest-cov, pytest-faker
- **Deployment:** Docker & Docker Compose

### Architecture Pattern
Clean layered architecture within modular Flask monorepo:
```
app/
├── <feature>/ (auth, vault, vault_lifecycle, workers, etc.)
│   ├── models.py       # SQLAlchemy ORM entities
│   ├── domain.py       # Domain model / aggregate roots / value objects
│   ├── repository.py   # Persistence layer (Protocol + Implementation)
│   ├── service.py      # Business logic layer
│   ├── routes.py       # HTTP API endpoints (via RESTX)
│   └── events.py       # Domain events (optional)
├── shared/             # Cross-cutting: database, errors, auth
├── platform/           # Configuration, extensions, middleware
└── cli/                # Command-line interface (Flask CLI)
```

## 8. KMS Startup Behavior

### How It Works
1. `create_app()` is called with parameter: `validate_kms=True` (production), `validate_kms=False` or `testing_bootstrap=True` (testing)
2. If `testing_bootstrap=True`:
   - `db.create_all()` creates all tables
   - `seed_kms()` creates an active LOCAL KMS config
   - `seed_rbac()` bootstraps RBAC users and roles
   - Then KMS validation proceeds
3. If `validate_kms=True`:
   - `KMSProviderFactory.resolve_active_provider()` is called
   - Queries for `KMSConfiguration WHERE is_active=True`
   - If found and provider_type='local': Returns LocalKMSProvider instance
   - If not found: Raises `KMSConfigurationError("No active KMS configuration found")`
   - If table doesn't exist (migrations not applied): Logs warning and skips validation

### Critical Security Rules
- ✅ No implicit fallback to default key
- ✅ No silent skip when config is missing (unless migrations not applied)
- ✅ Production failure is FAIL-CLOSED (app refuses to start)
- ✅ Master key never logged; only error about missing config

## 10. RotationWorker Architecture

### Entry Point
```python
def run_rotation_job(
    session: Session,
    audit_service: AuditService,
    encryption_service: EncryptionService,
    lifecycle_service: VaultLifecycleService,
    executor_registry: ExecutorRegistry,
    actor_id: UUID | None = None,
) -> dict:
    """Discover and rotate all eligible policies."""
```

### Algorithm
1. Query all `SecretRotationPolicy` where `status=ACTIVE` and `next_rotation_at <= now`
2. For each policy:
   - Begin SAVEPOINT (per-policy isolation)
   - Try `start_rotation()` → acquires CAS lock, transitions secret ACTIVE→ROTATING
   - If ConcurrencyError: skip (another worker won the lock)
   - Resolve executor via registry
   - Decrypt secret payload in-memory
   - Call `executor.execute(resource_id, plaintext)`
   - Handle result:
     - **Success:** Encrypt new bytes, call `complete_rotation()`, update policy timestamps
     - **Retryable:** Revert to ACTIVE, increment retry_count, keep next_rotation_at in past
     - **Terminal:** Mark secret DESYNCED, policy ERROR, audit severity HIGH
   - Commit SAVEPOINT (or rollback on unexpected error)
3. Return counters: {run_id, attempted, succeeded, retryable, terminal, no_executor, unexpected, skipped, duration_seconds}

### Concurrency Protection
- Per-policy SAVEPOINT ensures one failure doesn't cascade
- CAS on `start_rotation()` via `row_version` prevents duplicate rotations
- ConcurrencyError is treated as safe skip, not catastrophic failure

### Security Properties
- ✅ Plaintext credentials never logged, persisted, or propagated
- ✅ Audit payloads contain only encrypted bytes + metadata
- ✅ Executor is a pure function (no Flask/SQLAlchemy dependencies)
- ✅ No external I/O in stub executor (for testing)

### Test Coverage
- 19 tests covering all code paths
- Concurrency conflict detection
- Executor registry fallback
- State transitions for all outcomes
- Audit event verification
- Idempotency via CAS

## 12. Persistence & Compare-And-Swap (CAS) Architecture

### Invariant (Option A)
`VaultSecret.row_version` reflects the CURRENT persisted DB version.

### Update Contract
```python
def save(self, secret: Secret) -> None:
    # ... new insert case ...
    
    # For updates: atomic CAS with version check
    expected = secret.row_version  # Domain version before update
    stmt = (
        update(VaultSecret)
        .where(VaultSecret.id == secret.id, VaultSecret.row_version == expected)
        .values(
            status=secret.status,
            updated_at=secret.updated_at,
            row_version=expected + 1,  # Increment atomically
        )
    )
    result = self._session.execute(stmt)
    if result.rowcount == 0:
        raise ConcurrencyError(f"row_version mismatch: expected {expected}, got {current}")
    
    secret.row_version = expected + 1  # Sync domain object
```

### Why This Works
- Two independent sessions reading the same secret at version N
- Writer A: Commits N → N+1 successfully
- Writer B: Attempts N → N+1, but WHERE fails (now at N+1) → ConcurrencyError
- Loser never persists duplicate or corrupted state
- row_version increments exactly once per successful write

- Validates two-session atomic CAS scenario
